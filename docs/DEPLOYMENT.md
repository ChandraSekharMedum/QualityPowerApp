# Deploying Quality App Mobile to Another Environment

**QM-DEP-001 · 2026-08-18**

Covers `QualityAPP_Mobile` — the online phone app — and nothing else. The offline tablet app is
a separate solution and is deliberately out of scope here.

Everything below was read from the live `cus-con-sandbox` environment, not from memory.

---

## 1. What is being deployed

| | |
|---|---|
| Solution | `QualityAPP_Mobile` ("Quality App Mobile") |
| Version | 0.1.14.0, **unmanaged** |
| Publisher | `ColumbusGlobal`, prefix `cog` |
| Contents | 1 canvas app + F&O virtual-entity references |
| Canvas app | `cog_qualityappmobile_33e3d`, phone layout 640 x 1136 portrait |
| Screens | `MobOrders`, `MobResults`, `MobPhoto` |

**The app does use Dataverse tables — six of them — but every one is an F&O virtual table.**
That distinction is the whole story of this deployment, so it is worth being precise about:

| | Count | What it means for migration |
|---|---:|---|
| **Custom** (`cog_`) Dataverse tables | **0** | Nothing to create, nothing to migrate, no rows to move |
| **F&O virtual** tables (`mserp_`) | **6** | Must be *generated* in the target, not imported. See section 4 |
| of which bound as app data sources | 5 | Listed in `DatabaseReferences` |
| of which a dependency only | 1 | `InventQualityOrderLineEntityPowerApp` - see "Entity 6 is a trap" |

A virtual table is a live view onto F&O. It stores no data in Dataverse, which is why this
app has no storage footprint and no data to migrate — but it is still a Dataverse table and
still has to exist in the target environment before the app will open.

**There are no Power Automate flows, no connection references and no custom security roles.**
The app is online-only and talks to F&O directly, so there is no cache, outbox or sync
machinery to move. That makes this a genuinely small deployment.

## 2. F&O entities used — the complete list

Six F&O data entities, surfaced as Dataverse virtual tables by the **Finance and Operations
virtual entity provider** (`DataProviderId 2ac667f5-31d6-e911-a95e-000d3a110bbd`).

| # | F&O entity | Dataverse logical name | Used for | R/W |
|---|---|---|---|---|
| 1 | `InventQualityOrderHeaderEntity` | `mserp_inventqualityorderheaderentity` | the order list and its status | read |
| 2 | `PowerAppInventQOLineEntity` | `mserp_powerappinventqolineentity` | tolerances, unit, test variable id | read |
| 3 | `InventQualityOrderLineResultEntity` | `mserp_inventqualityorderlineresultentity` | the test worklist **and the result write** | **read + write** |
| 4 | `PowerAppsInventTestVariableOutcomeEntity` | `mserp_powerappsinventtestvariableoutcomeentity` | the allowed outcomes for option tests | read |
| 5 | `PowerAppFileSavingEntity` | `mserp_powerappfilesavingentity` | **photo attachments** | **write** |
| 6 | `InventQualityOrderLineEntityPowerApp` | `mserp_inventqualityorderlineentitypowerapp` | **nothing — see the warning below** | bound but unused |

### Fields actually written

Only two entities are written to.

**`InventQualityOrderLineResultEntity`** — one field per save, on an existing row:

| Field | When |
|---|---|
| `mserp_resultvalue` | numeric test |
| `mserp_qualitytestvariableoutcomeid` | option test |

F&O recalculates `mserp_testresult` (pass/fail) itself. The app never computes a verdict.

**`PowerAppFileSavingEntity`** — one new row per photo:

| Field | Value |
|---|---|
| `mserp_tablerefid` | `"0000"` (literal; F&O ignores it) |
| `mserp_displayordernumber` | quality order number |
| `mserp_testid`, `mserp_testsequence`, `mserp_linenum` | the test line — **mandatory**, see §7 |
| `mserp_filename` | generated, e.g. `QO000219-185024.jpg` |
| `mserp_formname` | **`"Quality"`** — exact value required, see §7 |
| `mserp_imagevarchar` | `data:image/jpeg;base64,...`, max 1,048,576 chars |
| `mserp_dataareaid` | company |

### Entity 6 is a trap, not a dependency

`InventQualityOrderLineEntityPowerApp` and `PowerAppInventQOLineEntity` **share the identical
display name "Quality order lines (mserp)"** in the Studio data source picker. Nothing
distinguishes them. Entity 6 covers only a fraction of orders (60 rows vs 154 in this
environment) and was bound by accident; entity 2 is the one the screens use, bound as
`Quality order lines (mserp)_1`.

Entity 6 is still bound in the app and must exist in the target, or the app will show an
unresolved data source. Do not "tidy" it away without re-testing.

## 3. Prerequisites in the target environment

1. **Dataverse environment linked to an F&O environment** with the virtual entity provider
   configured. Without it none of the `mserp_` tables exist and nothing below will work.
2. **The six entities generated as virtual tables.** They are not generated by default. See §4.
3. **F&O quality management configured** — test groups, tests, and variable outcomes for any
   option tests. An order with no outcomes configured shows every test as numeric.
4. **Licensing** for Power Apps and F&O for each inspector.
5. Deploying user needs System Customizer or System Administrator in the target Dataverse.

---

## 4. Generate the virtual entities (do this FIRST)

Solution import will not create them. In the target environment, for each of the six entities,
set `mserp_hasbeengenerated = true` on its catalogue row:

```
GET   mserp_financeandoperationsentities?$select=mserp_physicalname,mserp_hasbeengenerated
        &$filter=mserp_physicalname eq 'InventQualityOrderHeaderEntity'
PATCH mserp_financeandoperationsentities(<id>)   { "mserp_hasbeengenerated": true }
```

Generate all six:

```
InventQualityOrderHeaderEntity
PowerAppInventQOLineEntity
InventQualityOrderLineResultEntity
PowerAppsInventTestVariableOutcomeEntity
PowerAppFileSavingEntity
InventQualityOrderLineEntityPowerApp
```

`tools\Invoke-EntityGeneration.ps1` does this in batches; edit `tools\entity-targets.ps1` down
to these six. Generation is **asynchronous and slow — roughly 2-3 minutes per entity**. Verify
each table answers before continuing:

```
GET mserp_inventqualityorderheaderentities?$top=1
```

Change tracking is **off** for all six here and is not required.

## 5. Deploy

```powershell
# from the source environment
pac solution export --name QualityAPP_Mobile --path QualityAPP_Mobile.zip --managed false --overwrite

# against the target
pac org select --environment https://<target>.crm.dynamics.com/
pac solution import --path QualityAPP_Mobile.zip --force-overwrite --publish-changes
```

For a controlled release export `--managed true` instead and import the managed build; the app
is then not editable in the target, which is usually what you want for production.

`tools\Publish-CanvasApp.ps1 -SolutionName QualityAPP_Mobile` is the developer inner loop, not a
deployment tool. It swaps the canvas payload inside a freshly exported solution and re-imports.

## 6. After import — the step that is easy to miss

**Open the app in Power Apps Studio in the target and confirm the six data sources resolve.**

Canvas data sources are bound by table logical name. If an entity was not generated in §4, the
data source will not resolve and every formula using it fails — quietly, in the sense that the
app still opens and the affected galleries are simply empty.

If a data source needs re-adding, remember §2: **two tables share the display name "Quality
order lines (mserp)"**. The one the app needs is `mserp_powerappinventqolineentity`. The picker
cannot tell them apart, so add the one that is *not* already present and confirm afterwards by
exporting and reading `References/DataSources.json` inside the `.msapr`.

Then share the app with the inspector security group.

## 7. Two F&O behaviours that will bite in a new environment

Both were found by controlled probe and neither is documented.

**Photos need a test line.** A `PowerAppFileSavingEntity` row without `TestId` + `TestSequence`
+ `LineNum` is never processed by F&O. It sits in the staging entity indefinitely and no
attachment appears. The app enforces this by requiring a selected test.

**`FormName` must be exactly `"Quality"`.** With any other value — `InventQualityOrder` was
tried — F&O accepts the row, consumes it within seconds, and attaches the file to nothing. The
upload reports success and produces no attachment.

There is no `DocuRef`, `DocuValue` or `DocumentAttachment` entity in the catalogue, so **neither
of these can be verified over OData**. After deploying, attach one photo and look at the quality
order in the F&O client. That visual check is the only reliable confirmation.

---

## 8. Smoke test in the target

1. Open the app. The order list should populate and status chips read OPEN / PASS / FAIL, not
   black boxes. Black means a choice column is not resolving.
2. Open an order. Test lines should list, with an acceptable range shown for numeric tests.
3. Save a numeric result outside its range. It should come back **FAIL** — computed by F&O.
4. Save an option result. The outcome list should show the configured outcomes.
5. Attach a photo to a test line. The size readout must show real KB, not 0.
6. **Open that order in the F&O client and confirm the attachment is there.**

Step 6 is the one that cannot be skipped or automated.

---

## 9. Known constraints to tell the business

| Constraint | Detail |
|---|---|
| Online only | No offline support by design. No signal, no app. |
| Photo size | 1,048,576 base64 characters, about 786 KB of image. Enforced in-app before sending. |
| Photos attach to a test | There is no whole-order photo. |
| Verdicts are F&O's | The app never computes pass/fail. |
| Delegation | Fine at this scale (86 orders, 157 result rows). Above ~500 open orders the order picker needs re-testing for delegation against virtual tables. |

## 10. Licence cost

**Prices checked 2026-08-21** against Microsoft's public pricing pages. They are **USD list,
annual-commitment** figures. Microsoft's own note on the Power Apps pricing page applies:
prices "may not be reflective of actual list price due to currency, country, and regional
variant factors." Columbus's CSP or EA agreement will almost certainly differ. Treat the
numbers below as an order-of-magnitude estimate to size the conversation, not as a quote.

### 10.1 The question that decides the cost

Everything turns on one thing: **are the inspectors already licensed for Dynamics 365?**

Microsoft's rule is that Power Apps rights included with a Dynamics 365 licence may be used
"only within the context of the licensed Dynamics 365 application", and in the **same
environment** as that application.

`QualityAPP_Mobile` fits that description about as cleanly as an app can:

| Test | This app |
|---|---|
| Does it read/write only F&O data? | **Yes.** Six F&O virtual entities, listed in section 2 |
| Any custom (`cog_`) Dataverse tables? | **None.** All six tables are F&O virtual tables. Section 1 |
| Any premium connectors? | **None.** No connection references at all |
| Same environment as F&O? | **Yes.** Virtual entities only resolve in that environment |
| Does it do anything unrelated to SCM? | **No.** It is a quality-inspection front end |

So for a user who already holds a Dynamics 365 Supply Chain Management licence, this app is
an extension of the application they are licensed for, and **should carry no additional
licence cost**.

> **This is a contractual judgement, not a technical one.** "In the context of" is Microsoft's
> own phrase and it is deliberately interpretive. It must be confirmed with Columbus's
> licensing desk or the Microsoft partner account before being quoted to a customer. The
> technical facts in the table above are what a licensing specialist needs in order to rule,
> and every one of them was read from the live environment rather than assumed.

### 10.3 What it actually costs, by scenario

**Scenario A - inspectors already have D365 SCM.** The likely case, since they are inspecting
F&O quality orders and someone must be licensed to do that work in F&O anyway.

> **Incremental licence cost of deploying this app: $0.**

**Scenario B - inspectors are shop-floor users without a D365 licence.** They need a Power
Apps Premium licence each, because the app is then a standalone application from a licensing
point of view.

| Inspectors | Power Apps Premium | Annual |
|---:|---:|---:|
| 10 | $200 / month | $2,400 |
| 25 | $500 / month | $6,000 |
| 50 | $1,000 / month | $12,000 |
| 100 | $2,000 / month | $24,000 |

Scenario B is worth pressure-testing before accepting it. A user with no D365 licence can
still be blocked at the F&O end: the virtual entities enforce F&O security, so an unlicensed
user may be able to open the app and still see nothing. Confirm the F&O access model for
these users before assuming a Power Apps licence alone is sufficient.

### 10.4 Storage

This app adds **no Dataverse storage**. It has no custom tables and stores no rows; every
record it touches lives in F&O and is surfaced through virtual entities, which hold no data
in Dataverse. Photos are sent straight to F&O rather than staged locally.

The 250 MB Dataverse database entitlement that comes with a Power Apps Premium licence is
therefore ample, and the $40/GB add-on should not be needed for this solution.
